# Error Contract Enforcement

## Backend (Go)

All non-2xx responses from the backend **must** return this exact JSON shape:

```json
{
  "code":    "snake_case_error_code",
  "message": "human readable message",
  "errors":  { "field_name": ["Specific field validation message"] }
}
```

### Required Fields
- `code` – snake_case, uppercase (e.g., `bad_request`, `not_found`, `unauthorized`)
- `message` – human-readable string describing the failure
- `errors` – map of `field_name` → `["field-specific error"]` array (empty if none)
- `request_id` – optional, generated by middleware (for tracing)

### Built-in Error Types (backend/internal/api/errors.go)
- `ErrBadRequest` – 400, `code: "bad_request"`
- `ErrNotFound` – 404, `code: "not_found"`
- `ErrUnauthorized` – 401, `code: "unauthorized"`
- `ErrForbidden` – 403, `code: "forbidden"`
- `ErrInternal` – 500, `code: "internal_error"`
- `ErrNoActiveTermFutureExists` – 400, `code: "no_active_term_future_exists"`

### Validation Rules
- **No silent errors** – every `if err != nil` must call `WriteError` or equivalent
- **No void returns** – every async function must handle errors
- **No log-and-return** – log once at handler/service level, don't repeat in UI
- **No empty error maps** – if a field fails, include it in `errors` map

## Frontend (TypeScript)

All non-2xx responses from the frontend must use the same shape:

```ts
interface ApiErrorResponse {
  code: string;
  message: string;
  errors?: Record<string, string[]>;
  requestId?: string;
}
```

### Client Implementation
- `src/lib/api/client.ts` – centralizes error handling
- `src/lib/errors.ts` – `getErrorMessage(err)` helper that normalizes any error to the contract
- Every `useQuery`/`useMutation` must handle `isError` and render appropriately
- Form validation errors (400) must drive `form.setError` via `useForm`

## Cross-Cutting Rules

1. **Handler/Service Separation** – handlers are thin transport adapters; all DB access goes through `internal/services` and sqlc-generated queries
2. **No raw SQL in handlers** – never import `pgxpool` or `sqlc` directly in `internal/api/*`
3. **Error propagation** – every error must be written via `WriteError` (backend) or `getErrorMessage` (frontend)
4. **Consistent naming** – error codes follow the canonical list above

## Integration Points
- Triggered by `/error` command
- Uses `backend/internal/api/errors.go` as reference
- Uses `frontend/src/lib/api/client.ts` as reference
- Must pass through `testdb.DB(t)` integration tests

## Prerequisites
- `backend/internal/api/errors.go` (exists)
- `frontend/src/lib/api/client.ts` (exists)
- `testdb.DB(t)` pattern from existing tests
